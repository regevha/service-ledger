# SL-64: message parsing and PDF structural check (hand-off)

Two pure modules. No database, settings write, network or new package. Nothing is logged above DEBUG, and DEBUG lines hold fixed codes only.

## `backend/app/services/email_message.py`

`parse_message(raw, trusted_authserv_id=None, max_message_bytes=None) -> ParsedMessage`. It never raises.

- `from_address`: lower-case; `None` when there is no From, it is malformed, or it holds more than one address. Reply-To, Sender and Cc are never read.
- `message_key`: SHA-256 hex of the normalized Message-ID (trimmed, `<>` removed, lower-case). With no Message-ID: of `Date` plus the SHA-256 of every attachment.
- `is_auto_reply`: `Auto-Submitted` other than `no`, `Precedence` bulk/list/junk, or an empty `Return-Path` (bounce).
- `sender_verified`: `None` when no authserv-id is given (folder mailbox). Otherwise `True` only if the topmost `Authentication-Results` header written by that authserv-id shows `dmarc=pass`, or `dkim=pass` / `spf=pass` aligned (same domain, or a parent of the From domain). Other authserv-ids are ignored. A missing or unknown From gives `False`.
- `attachments`: tuple of `Attachment(position, data, declared_type)`, with `size_bytes` and `sha256`. A text/plain or text/html part with no filename and no `attachment` disposition is the body and is skipped. An attached message (`message/*`) is one attachment with empty data and is not opened. File names are not kept.
- `parts_limit_reached` (more than 50 parts), `too_large` (over `max_message_bytes`, not parsed), `unreadable` (parser failure).
- `authentication_verdict(headers, authserv_id, from_address)` is public for direct testing.

## `backend/app/services/pdf_safety.py`

`check_pdf(data, max_bytes=None) -> PdfVerdict(status, page_count, detail)`; `.ok` property. Never raises. `max_bytes` defaults to `settings.max_pdf_upload_bytes`.

Order: magic bytes at offset 0 (`not_pdf`), size (`too_large`), then `unsafe_pdf` with a fixed `detail`: `truncated` (no `%%EOF` in the last 2 KB), `forbidden_name`, `encrypted`, `open_action`, `no_pages`, `too_many_pages` (over 200), `too_many_objects` (over 50,000), `too_deep`, `too_slow` (10 s budget), `damaged_object`, `unreadable`.
`detail` is for tests and DEBUG only. The reply says "could not be accepted".

Forbidden names, as key or name value: `/JavaScript /JS /Launch /EmbeddedFile /EmbeddedFiles /RichMedia /XFA`, plus `/EF /FileAttachment /GoToE` (stricter than the spec). An `/OpenAction` must be a destination array or a `/GoTo` action. `/AA` is refused when it contains any forbidden name. The check is an object walk with pypdf (reaches compressed object streams) and a raw scan outside streams with `#xx` escapes decoded. `pypdfium2` is not used: it is native code, so it stays out of the intake path.

## For SL-65 (cases expected)

Messages: one valid PDF; Reply-To ignored; two From addresses -> `None`; no From; display-name trick; mixed case; auto-reply headers (each); Message-ID key stable across case and `<>`; no Message-ID key built from Date + attachment hashes; body skipped; attachment names and subject not anywhere in the result (`repr`); 51+ parts -> `parts_limit_reached`; `max_message_bytes`; garbage bytes -> no raise; Authentication-Results (pass/fail, untrusted authserv-id ignored, topmost wins, misaligned domain, `d=com` refused).
PDFs: clean passes with page count; PNG renamed `.pdf`, Office file, zip, script -> `not_pdf`; over limit; encrypted; truncated; garbage body; zero pages; JS (`add_js`); embedded file (`add_attachment`); `/Launch` or `/URI` OpenAction; `/J#61vaScript` escape; empty bytes.
Break-once checks: remove each forbidden name, the EOF check, and the magic check, and see a test fail.

## Open points

- Fillable vendor forms that carry format scripts (`/JS`) are refused, as the plan says. Check this against a real vendor form during the demo (the vendor PDFs were not opened here).
- A trailing-junk PDF with `%PDF-` not at byte 0 is refused as `not_pdf`.
