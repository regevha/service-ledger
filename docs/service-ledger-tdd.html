§0

Overview

SL-ARCH-001 decides what the system is and why. This document describes what got built.

SL-ARCH-001 is the product spec: it carries the evidence trail — which real BD Care service reports proved which template shape, why preventive_maintenance collapsed from three per-model rows to one — and the rationale a reviewer needs to trust a design decision. It deliberately doesn't say which file a function lives in or what a request looks like on the wire. This document is the other half: the backend as it exists today (FastAPI + Postgres, at commit-level accuracy as of this writing) — its modules, its data model in implementation terms, its request lifecycles, and the handful of decisions (an enum's exact values, a threshold's actual number) that implementation had to make and the spec left unstated.

Read SL-ARCH-001 first for why. Read this for where and how. §11 (Appendix) maps every section here back to the spec section it implements, so cross-referencing either direction is one lookup.

Scope

Backend only. The frontend is a paused Vite/React scaffold with no application code yet — out of scope here until that resumes. The three HTML review-screen demos (new-report, repair-review, PM-review, instrument-timeline) are UI mockups, not part of the running system, and aren't covered either.

§1

System architecture

One FastAPI process, one Postgres database, local disk for scans — nothing else runs yet.

The whole backend is a single FastAPI application (app.main:app) talking to a single Postgres database over SQLAlchemy, plus local disk for the scanned originals themselves. There is no queue, no cache, no separate worker process — SL-ARCH-001 §3 describes extraction as eventually async via a polling worker, but for MVP scale, classification and extraction both run inline inside the request that triggers them. The vision calls that would make classification and extraction real are not wired up at all yet: both are deterministic, in-process stub functions (§6) standing in for the Claude API call the request diagram below shows as not-yet-connected.

§3

Data model, as implemented

Five SQLAlchemy tables, field-for-field against spec §5 — plus the two enums the spec left unstated.

Every table in app/models.py uses a UUID primary key (uuid.uuid4 default) and Mapped/mapped_column SQLAlchemy 2.0 style. Four Python str, enum.Enum classes back Postgres native ENUM columns:

EnumValuesSource
ReportStatusdraft, classified, extracted, in_review, finalizedNamed explicitly in spec §5
ReportTypecalibration, repair, preventive_maintenanceNamed explicitly in spec §5
InstrumentStatusactive, maintenance, retiredNot specified in §5's table — an implementation default, flagged in the model's own docstring
ExtractionJobStatuspending, classifying, extracting, succeeded, failedNot enumerated in §5 — the obvious job lifecycle, kept minimal on purpose

The two implementation-only enums are exactly the kind of decision this document exists to record: reasonable, small, and easy to miss if only SL-ARCH-001 is read. Nothing else in the schema improvises — column names, nullability, and the JSONB fields all match §5 directly, including reports.instrument_id/template_id starting NULL under document-first intake, and extraction_jobs keeping classification separate from field_confidences because the former gates which template the latter even runs against.

TableNotable implementation detail
instrumentsinstrument_type is a plain String, not a native enum — deliberately, so adding a non-FACS instrument type later is a data change, not a migration
report_templatesfield_schema JSONB holds a {"fields": [...]} list; each field dict carries name/type/unit/notes and, for object[] fields, an item_schema
reportsextracted_fields defaults to {}, never NULL — every downstream read can assume a dict
attachmentspage_count is hardcoded to 1 — no PDF preprocessing wired in yet (§10)
extraction_jobsCascades from attachments, not from reports directly — a report's attachment carries its own job history

§4

Template resolution

One function, called from two places, so the manual picker can never suggest what auto-classify couldn't reach.

services/templates.py::resolve_template(db, instrument_type, report_type, model) is the single place a (instrument_type, report_type, model) triple becomes a ReportTemplate row: a model-specific row wins if one exists, else the model IS NULL fallback row is used. This is a deliberate guarantee, not a coincidence — GET /report-templates (the endpoint a manual fallback picker calls when classification is uncertain) and classify()'s own auto-resolve path both call this exact function rather than duplicating the precedence logic, so the two paths can never disagree about which template a given model resolves to.

§5

Document-first pipeline — request lifecycle

Six endpoints, one status column, two branches — confident classification resolves straight through, anything else waits for a manual pick.

Two things worth naming explicitly because they're easy to get wrong reading the router code in isolation: overriding a template via PATCH /reports/{id}/template discards extracted_fields back to {} whenever the template actually changes (checked by comparing template_id, not just accepting whatever the caller sends), and PATCH /reports/{id}/fields is allowed on a finalized report — corrections after finalizing simply overwrite in place, per §5/§6, since there's no audit log in MVP to preserve a "before" state anyway.

Spec drift, caught while writing this document

SL-ARCH-001 §12 still lists "the classification confidence threshold" as an open question — whether it should be stricter than the field-level default rather than inheriting it. The code already answers this: config.py sets classification_confidence_threshold = 0.85 against field_confidence_threshold = 0.7, with a comment explaining exactly the reasoning §12 asks for (a wrong report-type guess is costlier than one wrong field). The implementation made the call; the spec's open-questions list just hasn't been told yet. Worth a one-line fix to §12 so the two documents agree.

§8

Testing strategy

Real Postgres, not SQLite — because the whole point of the design being tested is Postgres-specific.

tests/conftest.py points at a separate calibration_ledger_test database rather than an in-memory substitute, because §5's JSONB design and its native-enum columns are exactly the kind of thing SQLite doesn't faithfully stand in for. Tables are cleaned between tests with TRUNCATE ... RESTART IDENTITY CASCADE rather than a rollback-per-test transaction — simpler to reason about, and it sidesteps a real gotcha this project hit: pairing a test session with an already-open connection transaction needs SAVEPOINT bookkeeping that a plain session.commit() breaks, since commit ends the outer transaction the test fixture was counting on.

TestCovers
test_confident_classification_resolves_straight_throughThe auto-resolve branch: both guesses above threshold, straight to extraction
test_uncertain_report_type_falls_back_to_manual_pick_then_finalizesThe full manual-fallback path, reproducing the real sample document's asymmetry — end to end through finalize
test_cannot_finalize_a_bare_draftThe 409 guard on finalizing a report with no extraction yet
test_overriding_template_discards_prior_extractionSwitching templates after extraction wipes extracted_fields, per §5/§6

§9

Known gaps

What today's implementation defers, and why each one is safe to defer.

  • classify()/extract() are stubs. Deterministic and hash-seeded rather than random, with a special case that reproduces the original sample document's real asymmetry (confident instrument, borderline report type) so both pipeline branches stay exercisable without a live API key. The next real engineering step: swap each function's body for an actual Claude vision call — same signature, same callers, no router or schema change needed.
  • No background worker. Classification and extraction run inline in the request. Spec §3's async-worker design doesn't change the API contract, so this is a pure implementation swap whenever request latency makes it necessary — not before.
  • No PDF preprocessing. page_count is hardcoded to 1; multi-page splitting (spec §4 step 2) has nothing real to run against until live extraction exists.
  • No audit log or template versioning. A confirmed MVP tradeoff (spec §10), not an oversight — becomes necessary the moment a second technician can edit another's report.

These, plus the two evidence gaps (a FACSAria III PM document, a real FACSDiscover S8 calibration document — both spec-level, not implementation-level) are tracked with checkable status in the project's build tracker artifact, published separately.
