§0

Overview

SL-ARCH-001 decides what the system is and why. This document describes what got built.

SL-ARCH-001 is the product spec: it carries the evidence trail — which real BD Care service reports proved which template shape, why preventive_maintenance collapsed from three per-model rows to one — and the rationale a reviewer needs to trust a design decision. It deliberately doesn't say which file a function lives in or what a request looks like on the wire. This document is the other half: the system as it exists today (FastAPI + Postgres + a background worker on the backend, a React/Vite frontend, at commit-level accuracy as of this writing) — its modules, its data model in implementation terms, its request lifecycles, and the handful of decisions (an enum's exact values, a threshold's actual number) that implementation had to make and the spec left unstated.

Read SL-ARCH-001 first for why. Read this for where and how. §11 (Appendix) maps every section here back to the spec section it implements, so cross-referencing either direction is one lookup.

Scope

Covers the backend and the frontend that now consumes it (§7). v0.1 of this document scoped the frontend out as "a paused Vite/React scaffold with no application code yet" — that stopped being true within days of v0.1 shipping, and this revision corrects it. The three original HTML review-screen demos (new-report, repair-review, PM-review, instrument-timeline) are superseded by the real frontend and are kept only as historical mockups, not part of the running system.

§1

System architecture

One FastAPI process, one Postgres database, local disk for scans, and a separate background worker that does the actual Claude calls.

The system is a FastAPI application (app.main:app) talking to a single Postgres database over SQLAlchemy, plus local disk for the scanned originals themselves, plus a dedicated worker process (python -m app.worker). SL-ARCH-001 §3's "single background worker process, polling a job table in Postgres" is implemented exactly as described: POST /attachments/{id}/classify and .../extract only insert a pending row into extraction_jobs and return 202 immediately (§5, §9); the worker claims rows with with_for_update(skip_locked=True) and is what actually runs classify()/extract(). Those two functions are deterministic, hash-seeded stubs by default; behind the use_live_claude setting (§8) they instead send the scanned PDF to the real Claude API via a shared client module (services/claude_client.py) — the vision call the previous revision of this diagram showed as not-yet-connected now exists and is unit-tested (§9), just off by default.

§3

Data model, as implemented

Five SQLAlchemy tables, field-for-field against spec §5 — plus the three enums the spec left unstated.

Every table in app/models.py uses a UUID primary key (uuid.uuid4 default) and Mapped/mapped_column SQLAlchemy 2.0 style. Five Python str, enum.Enum classes back Postgres native ENUM columns:

EnumValuesSource
ReportStatusdraft, classified, extracted, in_review, finalizedNamed explicitly in spec §5
ReportTypecalibration, repair, preventive_maintenanceNamed explicitly in spec §5
InstrumentStatusactive, maintenance, retiredNot specified in §5's table — an implementation default, flagged in the model's own docstring
ExtractionJobStatuspending, classifying, extracting, succeeded, failedNot enumerated in §5 — the obvious job lifecycle, kept minimal on purpose
ExtractionJobKindclassify, extractNot named in §5, which describes "one classify-then-extract attempt" in prose — the real endpoints submit these as two separate jobs with a manual-confirm checkpoint possibly in between (§5/§9), so each stage needs its own job row and its own kind

The three implementation-only enums are exactly the kind of decision this document exists to record: reasonable, small, and easy to miss if only SL-ARCH-001 is read. Nothing else in the schema improvises — column names, nullability, and the JSONB fields all match §5 directly, including reports.instrument_id/template_id starting NULL under document-first intake, and extraction_jobs keeping classification separate from field_confidences because the former gates which template the latter even runs against.

TableNotable implementation detail
instrumentsinstrument_type is a plain String, not a native enum — deliberately, so adding a non-FACS instrument type later is a data change, not a migration
report_templatesfield_schema JSONB holds a {"fields": [...]} list; each field dict carries name/type/unit/notes and, for object[] fields, an item_schema — itself a list of {name, type} columns, not a {name: type} dict, since Postgres's JSONB storage only preserves a JSON array's element order, not an object's key order
reportsextracted_fields defaults to {}, never NULL — every downstream read can assume a dict
attachmentsfile_type is the media type sniffed from the file's bytes at upload, not the client's declared content type. page_count is hardcoded to 1 — nothing counts PDF pages (§10)
extraction_jobsCascades from attachments, not from reports directly — a report's attachment carries its own job history

§4

Template resolution

One function, called from two places, so the manual picker can never suggest what auto-classify couldn't reach.

services/templates.py::resolve_template(db, instrument_type, report_type, model) is the single place a (instrument_type, report_type, model) triple becomes a ReportTemplate row: a model-specific row wins if one exists, else the model IS NULL fallback row is used. This is a deliberate guarantee, not a coincidence — GET /report-templates (the endpoint a manual fallback picker calls when classification is uncertain) and classify()'s own auto-resolve path both call this exact function rather than duplicating the precedence logic, so the two paths can never disagree about which template a given model resolves to.

§5

Document-first pipeline — request lifecycle

Six endpoints, one status column, two branches — confident classification resolves straight through, anything else waits for a manual pick. Classify and extract are now submit-and-poll, not synchronous calls.

Upload validation. The upload route decides what the file is before it writes anything: documents.detect_media_type() checks the leading bytes (%PDF-, the PNG/JPEG/GIF signatures, RIFF…WEBP) and ignores the client's content type and filename, so an image scan mislabelled as a PDF — which a scanner app can produce — is stored with its true type and sent to Claude as an image block instead of failing at the API. An empty file is a 422; an unrecognised type (HEIC included, which the API doesn't take) is a 415; a file over the limit for its type — max_pdf_upload_bytes (20 MB) or max_image_upload_bytes (5 MB) — is a 413 whose message states the file's size and the limit. These mirror the model API's own limits so a rejected file fails at once with advice, not minutes later as a failed job. Nothing is split, rotated or resized; the PDF page count isn't checked.

Serial matching. Only instruments.serial_number is unique — several instruments can share a model — so classification also asks Claude for the serial printed on the document (instrument_serial plus instrument_serial_confidence in the same forced tool call) and match_serial() compares it with the fleet after normalising both sides (upper case, letters and digits only, so mp 665158-0000057 equals MP6651580000057). The outcome is reported on ClassificationResult.serial_match: matched when it matches one instrument whose model agrees with the model guess, model_conflict when it matches an instrument of a different model, not_found when no fleet instrument carries that serial, and not_read when none was read. Only matched with a serial confidence at or above classification_confidence_threshold picks the instrument for auto-resolution (resolved_instrument_id, which still needs the instrument and report-type guesses to clear the threshold and a template to exist); a conflict is never auto-resolved, and not_found, not_read or a low-confidence read falls back to the older rule — exactly one unit of the model auto-selects it, several leave the choice to the technician. suggested_instrument_id is the separate, softer signal the intake screen preselects: the serial's instrument for matched or model_conflict, otherwise the only unit of the model, if there is one. The intake screen shows a warning or info banner (#serial-notice) saying which happened. The stub "reads" a serial only when the uploaded file's own name contains a fleet instrument's serial (e.g. scan_A47291.pdf), so every path is testable without an API key by choosing a file name, and every other stub upload behaves as before.

The service-visit date. reports.report_date is a column on every report, not a template field, but it's read off the document by the same extraction call: the tool schema always asks for report_date (YYYY-MM-DD) and its confidence alongside the template's own fields, and the prompt tells Claude which date that is — on a BD Care work order, the LABOR table's date, not the service-contract or calibrated-tool dates printed on the same form — and how to tell the day/month order, which varies between BD forms (a February 2026 S8 PM report prints 02/10/2026 for 10 February; an older form prints 18/04/2021), from any date on the form with a part greater than 12. The answer is validated before it's used: anything that isn't an ISO date, or falls before 1990 or after tomorrow, is dropped with a warning and its confidence set to 0. The worker writes a date it got and leaves the existing value alone when it got none. The confidence travels in field_confidences under the key report_date, which TemplateFieldIn reserves so no template field can collide with it, and the review screen shows the date as an editable field with that confidence, saved through PATCH /reports/{id}/fields. Until this existed nothing in the app set the column, so the Reports date filters, the trend chart's x-axis and the CSV export order only worked for seeded data; the trend chart and export now also fall back to creation date for any report that still has none.

Two things worth naming explicitly because they're easy to get wrong reading the router code in isolation: overriding a template via PATCH /reports/{id}/template discards extracted_fields back to {} whenever the template actually changes (checked by comparing template_id, not just accepting whatever the caller sends), and PATCH /reports/{id}/fields is allowed on a finalized report — corrections after finalizing simply overwrite in place, per §5/§6, since there's no audit log in MVP to preserve a "before" state anyway. A third, worth adding in this revision: the worker re-checks report.template_id/instrument_id before running an extract job even though the router already checked the same condition synchronously at submit time — a second attachment on the same report can race the first between submit and pickup, so the worker doesn't trust the state it was enqueued under.

SL-ARCH-001 §12 once listed "the classification confidence threshold" as an open question — whether it should be stricter than the field-level default rather than inheriting it. The code already answers this: config.py sets classification_confidence_threshold = 0.85 against field_confidence_threshold = 0.7, with a comment explaining exactly the reasoning §12 asks for (a wrong report-type guess is costlier than one wrong field). The implementation made the call, and SL-ARCH-001 v0.13 now records it as resolved, so the two documents agree.

§9

Testing strategy

Real Postgres, not SQLite — because the whole point of the design being tested is Postgres-specific.

tests/conftest.py points at a separate service_ledger_test database (the E2E suite below uses its own service_ledger_e2e, reset before every run) rather than an in-memory substitute, because §5's JSONB design and its native-enum columns are exactly the kind of thing SQLite doesn't faithfully stand in for. Tables are cleaned between tests with TRUNCATE ... RESTART IDENTITY CASCADE rather than a rollback-per-test transaction — simpler to reason about, and it sidesteps a real gotcha this project hit: pairing a test session with an already-open connection transaction needs SAVEPOINT bookkeeping that a plain session.commit() breaks, since commit ends the outer transaction the test fixture was counting on.

The suite has grown well past the original four happy/uncertain-path tests to 298 tests across 22 files, tracking every module added since (§2):

On top of the backend suite, the frontend (§7) has its own 27-spec Playwright end-to-end suite across 14 files driving the real UI against a stub backend — not covered by the previous revision of this document, since the frontend didn't exist yet.

Coverage. pytest --cov reads backend/.coveragerc: line and branch coverage over app/, with the two demo-data seed scripts and testing/reset_db.py left out on purpose (they are dev conveniences; the e2e suite runs reset_db for real) and a fail_under floor of 95% so a change that lowers coverage fails the run. The backend measures about 97% including branches. The race-handling branches that were the largest uncovered block are now tested directly (test_race_conditions.py); what remains is mostly small defensive guards in analytics and extraction, the real get_db dependency (tests override it) and the Claude client's error wrapper. The frontend has no unit tests; the Playwright suite is its only automated check, and npm run test:e2e:coverage measures what it reaches by running the suite against an Istanbul-instrumented build: about 91% of lines and 76% of branches, with a floor of 88% / 70%. The least-covered files are TemplateManager.tsx (about 75% of lines) and IntakeFlow.tsx (about 88%), mostly error and edge branches.

§10

Known gaps

What today's implementation still defers, now that two of the previous revision's four gaps are closed.

  • classify()/extract() are live-capable, but stub by default. Resolved from "are stubs" in the previous revision. A real Claude vision call exists behind use_live_claude (§1, §8) — the stub is now a deliberate default/demo mode, not the only path. What's still open: nothing structural, but the live path has only been smoke-tested by hand (playwright.live.config.ts), not run against the full evidence set SL-ARCH-001 calls for — in particular a real FACSDiscover S8 PM report (expected report date 2026-02-10, serial matched to the fleet's S8) hasn't been read by live Claude in this build, only transcribed by hand.
  • No PDF preprocessing — and none planned. SL-ARCH-001 v0.16 drops the "Preprocess" step: Claude reads the PDF or image natively, so the only pre-model step is the validation in §5. page_count is still hardcoded to 1 and a PDF's page count isn't checked, so a very long PDF would be refused by the model API, not by us.
  • HEIC is not accepted. The model API doesn't take it, so a phone photo has to be exported as JPEG or PNG. Converting on upload would close this if it proves a nuisance.
  • No audit log or template versioning. Unchanged. A confirmed MVP tradeoff (spec §10), not an oversight — becomes necessary the moment a second technician can edit another's report.
Closed since the previous revision

No background worker — resolved. app/worker.py implements spec §3's polling-worker design exactly (§1); classify/extract are now submit-and-poll (§5), not inline. Frontend out of scope — resolved by simply no longer being true: see §7.

These, plus the two evidence gaps (a FACSAria III PM document, a real FACSDiscover S8 calibration document — both spec-level, not implementation-level) are tracked with checkable status in the project's build tracker artifact, published separately.
